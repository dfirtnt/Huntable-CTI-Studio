# Configuration Reference

Configure providers and credentials in **Settings**, and agent models and prompts on the **Workflow -> Config** tab. Deployment settings live in `.env` and `docker-compose.yml`; source definitions and workflow settings also live in PostgreSQL.

## Configuration Files

### Environment Variables (.env)

Create deployment credentials and service settings with setup:
```bash
./setup.sh --no-backups
```

### Docker Compose (docker-compose.yml)

Defines service topology, port mappings, and volume mounts.

Compose reads `.env` for interpolation; it does not automatically inject every entry into every container. A variable must appear in a service's `environment` mapping to reach that service. Literal values in Compose override attempts to set the same value through `.env`.

### Database Settings

**Settings** stores provider switches, credentials, and integration settings in `app_settings`. **Workflow -> Config** stores the active workflow's thresholds, models, extractor switches, and prompts. For provider credentials, saved database values take precedence over environment values.

### Source Configuration (config/sources.yaml)

Seeds CTI feeds and sources. Existing installations read the `sources` table at runtime. See [Source Configuration Precedence](../guides/source-config.md) for startup and manual-sync behavior.

## Port Mappings

### Default Ports

| Service | Host Port | Container Port | Purpose |
|---------|-----------|----------------|---------|
| Web/API | 8001 | 8001 | Main FastAPI application |
| PostgreSQL | 5432 | 5432 | Database |
| Redis | 6379 | 6379 | Cache and message broker |
| LM Studio (optional) | 1234 | N/A | External host service; port configured in LM Studio |

### Customizing Ports

To change the host port for the web application, edit `docker-compose.yml`:

```yaml
services:
  web:
    ports:
      - "8011:8001"  # Map host port 8011 to container port 8001
```

After changing ports:
```bash
docker compose up -d web
```

Open `http://localhost:8011` and check `http://localhost:8011/health`. Update URLs in the examples below to match. Port 8002 is reserved for the isolated test web service; run tests through `python3 run_tests.py` rather than pointing them at the live app.

### Troubleshooting Port Conflicts

Check if a port is in use:
```bash
lsof -i :8001
```

To resolve conflicts, either stop the conflicting service or change the host port in `docker-compose.yml` as shown above.

## Environment Variables Reference

The tables describe runtime inputs. Check `docker-compose.yml` before using `.env` to override one: several inputs below are read by Python but are not passed through by the shipped Compose configuration.

### Core Infrastructure

| Variable | Purpose | Default | Required |
|----------|---------|---------|----------|
| `DATABASE_URL` | PostgreSQL connection string | Compose builds it for database `cti_scraper`, user `cti_user`, from `POSTGRES_PASSWORD` | Yes |
| `POSTGRES_PASSWORD` | PostgreSQL password | Generated by setup | Yes |
| `MAINTENANCE_API_TOKEN` | Shared secret for web-to-maintenance backup/restore requests | Empty unless configured | Yes for web backup/restore |
| `REDIS_URL` | Redis connection | `redis://redis:6379/0` | Yes |
| `SOURCES_CONFIG` | Path to sources YAML | `config/sources.yaml` | No |
| `ENVIRONMENT` | Runtime environment label | `development` (literal in Compose) | No |
| `APP_ENV` | Security configuration environment | `development` | No |
| `DISABLE_SOURCE_AUTO_SYNC` | Skip YAML-to-DB sync on startup | `false`; add to the web service environment to override | No |
| `SECRET_KEY` | Signs CSRF tokens | Generated by `./setup.sh` | In production when CSRF is active |

### Authentication and Access Control

Auth, RBAC, and CSRF are configured entirely via environment variables (`AUTH_MODE`, `TRUSTED_HOSTS`, `CORS_ALLOWED_ORIGINS`, `CSRF_ENABLED`, the `AUTH_*` trusted-header and group-mapping variables). The canonical reference is [Authentication](../guides/authentication.md); for the Entra ID / oauth2-proxy front door see [Enterprise SSO Setup](../guides/enterprise-sso.md). Parsing and fail-closed production validation live in `src/web/security/config.py`.

### Celery Configuration

| Variable | Purpose | Default |
|----------|---------|---------|
| `CELERY_BROKER_URL` | Broker and result-backend URL when `REDIS_URL` is absent | `redis://redis:6379/0` |
| `CELERY_MAX_TASKS_PER_CHILD` | Tasks per worker child before that child is replaced | `50` |

Compose sets `REDIS_URL` directly. To change the broker or worker child limit, update the relevant worker and scheduler environment mappings, then recreate those services.

### LLM Provider Keys

| Variable | Purpose | Required |
|----------|---------|----------|
| `OPENAI_API_KEY` | OpenAI API key | No |
| `ANTHROPIC_API_KEY` | Anthropic Claude API key | No |

**Keys entered during setup** are written to `.env` and passed into the application by Compose. You do not need to enter them again in Settings. Enable the provider in **Settings -> Agentic Workflow Configuration**, save, then select its models on **Workflow -> Config**. A preset does not configure credentials or enable a provider globally.

**Credential fields never show a stored value.** The settings API does not return secrets to the browser, so every credential input loads empty regardless of whether one is configured. The line under the field is what tells you: *Configured* (with a short hint and a **Clear stored** control) or *Not set*. Type a new value to replace what is stored; leaving the field empty leaves it untouched. Removing a credential is a deliberate act via **Clear stored**, never a side effect of an empty field.

### Workflow-Specific LLM Configuration

Use **Settings -> Agentic Workflow Configuration** for credentials and provider switches. Credential resolution is: non-empty saved Settings value, then `WORKFLOW_*_API_KEY`, then the general provider key.

| Setting / variable | Purpose | Resolution or default |
|--------------------|---------|-----------------------|
| `WORKFLOW_OPENAI_API_KEY` | OpenAI workflow credential | Falls back to `OPENAI_API_KEY` |
| `WORKFLOW_ANTHROPIC_API_KEY` | Anthropic workflow credential | Falls back to `ANTHROPIC_API_KEY` |
| `WORKFLOW_OPENAI_ENABLED` | OpenAI provider switch | Saved Settings, then environment |
| `WORKFLOW_ANTHROPIC_ENABLED` | Anthropic provider switch | Saved Settings, then environment |
| `WORKFLOW_LMSTUDIO_ENABLED` | LM Studio provider switch | Saved Settings, then environment; Compose defaults to `true` |
| `WORKFLOW_CODEX_ENABLED` | Codex subscription provider switch | Saved Settings, then environment; Compose defaults to `false` |

Without an explicit OpenAI/Anthropic switch, the provider picker defaults to disabled, while `LLMService` defaults to enabled when a key exists. Save an explicit switch in Settings to keep both paths consistent. LM Studio defaults to disabled in Python when no switch is supplied, but Compose supplies `true` unless overridden.

The shipped Compose file passes workflow-specific API-key overrides to both workers, but not to `web`. It does not pass `WORKFLOW_OPENAI_ENABLED` or `WORKFLOW_ANTHROPIC_ENABLED`. Settings is the consistent way to configure these across services.

**Fallback models:** select each agent's model on **Workflow -> Config**, or import a preset. Those explicit selections override these `LLMService` fallback values:

| Variable | Python fallback |
|----------|-----------------|
| `WORKFLOW_OPENAI_MODEL` | `gpt-4o-mini` |
| `WORKFLOW_ANTHROPIC_MODEL` | `claude-sonnet-4-5` |
| `WORKFLOW_CODEX_MODEL` | `gpt-5.6-luna` |

Compose passes through only the Codex model variable from this table. The provider picker separately suggests Anthropic `claude-sonnet-4-6` and the first discovered Codex model; changing a fallback variable does not change saved agent models or the picker's suggestions.

## Optional Codex Subscription Provider

Codex uses a managed ChatGPT login rather than an API key. Enable Codex in **Settings -> Agentic Workflow Configuration** and save. Alternatively, set `WORKFLOW_CODEX_ENABLED=true` in `.env` and recreate `web`, `worker`, and `workflow_worker`.

Authenticate the shared workflow-worker state volume once:

```bash
docker compose exec workflow_worker codex login --device-auth
```

`--device-auth` is required here. Plain `codex login` starts a browser-callback
listener on port 1455 inside the container, which a host browser cannot reach;
the device-code flow prints a URL and code to open in your own browser instead.
The credential is written to the shared `codex_auth` volume, so `web` and both
workers pick it up without a restart.

Use **Test subscription** in Settings (or `POST /api/settings/codex/test`) to verify connectivity without running a workflow. Then select a model listed for that login on **Workflow -> Config**, or load a matching Codex preset.

## Optional LM Studio LLM Provider

LM Studio is not an application dependency. Configure this section only if you choose LM Studio for LLM inference. Embeddings are generated inside the application with sentence-transformers and do not call LM Studio.

| Variable | Purpose | Default |
|----------|---------|---------|
| `LMSTUDIO_API_URL` | LM Studio API base URL | `http://host.docker.internal:1234/v1` |
| `LMSTUDIO_MODEL` | Default LM Studio model | `deepseek/deepseek-r1-0528-qwen3-8b` (hardcoded in `docker-compose.yml`; `.env` value is not passed through) |
| `LMSTUDIO_MODEL_RANK` | Model for ranking agent | `qwen/qwen3-4b-2507` (hardcoded in `docker-compose.yml`; `.env` value is not passed through) |
| `LMSTUDIO_MODEL_EXTRACT` | Model for extraction agent | `qwen/qwen3-4b-2507` |
| `LMSTUDIO_MODEL_SIGMA` | Model for Sigma generation | `qwen/qwen3-4b-2507` |
| `LMSTUDIO_TEMPERATURE` | Fallback temperature when no per-agent value is supplied | `0.0` |
| `LMSTUDIO_TOP_P` | Fallback top-p when no per-agent value is supplied | `0.9` |
| `LMSTUDIO_SEED` | Optional sampling seed | Unset |
| `LMSTUDIO_MAX_CONTEXT` | Fallback context estimate for reasoning models | `32768` tokens |

Enable LM Studio and set its server URL in **Settings -> Agentic Workflow Configuration**, then select loaded models on **Workflow -> Config**. The shipped host URL uses `host.docker.internal` so containers can reach a server on your Mac or PC.

Configure the actual context window when loading the model in LM Studio. `LMSTUDIO_CONTEXT_LENGTH_<model_slug>` supplies an application-side estimate override; replace `/` and `-` in the model ID with `_`. These overrides can differ between Compose services and do not resize a loaded model. See [LM Studio Integration](../llm/lmstudio.md#context-length).

## Workflow Presets

Quickstart presets are full workflow snapshots: thresholds, model assignments, extractor switches, platform selection, and prompts. They replace the active workflow configuration; they do not include provider credentials, enable providers globally, or authenticate Codex. Configure the matching provider in Settings first.

Quickstart presets (v2 format, always committed to the repo) are in `config/presets/AgentConfigs/quickstart/`:

|-------------|----------|----------------|
| `Quickstart-anthropic-sonnet-4-6.json` | Anthropic | `claude-sonnet-4-6` |
| `Quickstart-anthropic-haiku-4-5.json` | Anthropic | `claude-haiku-4-5-20251001` |
| `Quickstart-openai-gpt-4.1-mini.json` | OpenAI | `gpt-4.1-mini` |
| `Quickstart-openai-gpt-4.1.json` | OpenAI | `gpt-4.1` |
| `Quickstart-openai-gpt-4o.json` | OpenAI | `gpt-4o` |
| `Quickstart-openai-gpt-4o-mini.json` | OpenAI | `gpt-4o-mini` |
| `Quickstart-openai-gpt-5.json` | OpenAI | `gpt-5` |
| `Quickstart-openai-gpt-6-luna.json` | OpenAI | `gpt-6-luna` |
| `Quickstart-codex-gpt-5.6-sol.json` | Codex | `gpt-5.6-sol` |
| `Quickstart-codex-gpt-5.6-terra.json` | Codex | `gpt-5.6-terra` |
| `Quickstart-codex-gpt-5.6-luna.json` | Codex | `gpt-5.6-luna` |
| `Quickstart-codex-gpt-6-luna.json` | Codex | `gpt-6-luna` |
| `Quickstart-LMStudio-Qwen3.json` | LM Studio | `qwen/qwen3-8b` |
| `Quickstart-LMStudio-Gemma4B.json` | LM Studio | `google/gemma-3-4b` |

All paths are relative to `config/presets/AgentConfigs/quickstart/`.

All 14 files assign the listed model to the rank, extraction fallback, seven extractors, and SIGMA agent. **Ranking is disabled**, all seven extractors are enabled, and the stored platform selection is **Windows**. Shared thresholds are junk filter `0.8`, minimum hunt score `97`, ranking `6`, and similarity `0.5`. Codex presets set extractor reasoning effort to `low`. Importing one can change these values in an existing workflow.

**How to load a preset**

1. Enable and test the matching provider in **Settings -> Agentic Workflow Configuration**. The exact preset model must be available to your API account, Codex login, or local server.
2. Open **Workflow -> Config**. Use **Export Preset** to save the current configuration if needed.
3. Choose **Import Preset** from the config actions menu, or **Import Preset from file** in the preset modal, and select a JSON file from `config/presets/AgentConfigs/quickstart/`.
4. Confirm replacement, then check model selections, extractor switches, ranking, platform selection, and thresholds before running an article. Enable ranking if you want that stage to run.

**Private presets**: To keep presets out of version control, put JSON files in `config/presets/private/`. That directory is gitignored (only `*.json` there); use **Import Preset from file** to load from it.

### Create a Baseline Preset

1. On **Workflow -> Config**, configure the provider/model assignments, prompts, thresholds, platform selection, and extractor switches you want in the baseline. You can import an existing quickstart preset as a starting point.
2. Choose **Export Preset** from the config actions menu and name the downloaded JSON. The export endpoint validates the supplied configuration and writes v2 UI-ordered JSON; it does not generate provider variants or read seed prompts from disk.
3. Save the file in `config/presets/private/` for personal use. To add a shipped quickstart, place it in `config/presets/AgentConfigs/quickstart/` with a descriptive `Quickstart-*.json` filename and update the preset tables.
4. Check shipped preset quality from the repository root:

   ```bash
   uv run python run_tests.py unit --paths tests/config/test_quickstart_preset_quality.py
   ```

There is no dedicated script that creates the complete quickstart set from an empty directory. When adding provider/model variants, update every intended model-bearing agent section; changing only the filename or ExtractAgent fallback leaves other agents assigned to the old model.

### Normalize Existing Quickstart Presets

To validate and rewrite existing quickstart files into canonical UI order, run from the repository root:

```bash
uv run python scripts/normalize_quickstart_presets.py
```

This script only visits existing `quickstart/*.json` files. It migrates supported formats, supplies supported compatibility defaults and missing metadata, and rewrites canonical UI order. It does not create missing files, refresh prompts from `src/prompts/`, or import presets into the running app. Required-field failures are reported as skipped files; `Updated` means a file was rewritten, not that prompts were refreshed. To refresh the embedded prompts from `src/prompts/`, run `uv run --frozen python scripts/build_quickstart_prompts.py`.

Seed prompt edits do not update live prompts. Use the workflow editor for live changes; see [Edit Agent Prompts](../guides/edit-prompts.md).

## Langfuse Observability

| Variable | Purpose | Notes |
|----------|---------|-------|
| `LANGFUSE_PUBLIC_KEY` | Langfuse public key | Required to enable tracing |
| `LANGFUSE_SECRET_KEY` | Langfuse secret key | Required to enable tracing |
| `LANGFUSE_HOST` | Langfuse Cloud host URL | Optional; runtime default is `https://us.cloud.langfuse.com` |
| `LANGFUSE_PROJECT_ID` | Langfuse project ID | Optional; improves workflow trace deep links in the UI |

Configure Langfuse through environment variables or the Settings UI. Settings stored in the web UI take precedence over the same values in the environment.

Huntable CTI Studio supports **Langfuse Cloud only**. Local or self-hosted Langfuse deployments are outside this project's supported and tested configurations.

Set `LANGFUSE_HOST` to the host shown for your Langfuse Cloud project. If unset, the runtime defaults to `https://us.cloud.langfuse.com`. Keep the host and credentials from the same project and region.

Security note: Langfuse receives workflow and LLM telemetry. Depending on the workflow path, traces may contain prompts, article content, extracted observables, outputs, and metadata. Enable Langfuse only where external cloud tracing is acceptable for your data.

See [Langfuse Setup](../guides/langfuse-setup.md) for the full setup and verification workflow.

## SIGMA / GitHub Integration

The app submits approved SIGMA rules via GitHub PRs. **Setup is automated during `./setup.sh`.**

**During setup.sh (interactive):**

1. Create a repo at [github.com/new](https://github.com/new) (e.g. `Huntable-SIGMA-Rules`)
2. When prompted, enter `owner/repo` (e.g. `myuser/Huntable-SIGMA-Rules`)
3. The script clones to `../Huntable-SIGMA-Rules`. A repo with no rules yet gets `.huntable/rule-layout.yml`, the table that decides each published rule's directory; rule directories appear with the first PR

**Before submitting a PR:**

- Add your **GitHub Personal Access Token** in **Settings -> GitHub** (repo scope)
- Create token at [github.com/settings/tokens](https://github.com/settings/tokens)

**Non-interactive:** Set `SIGMA_GITHUB_REPO=owner/repo` before running `./setup.sh --non-interactive` to clone automatically.

| Variable | Purpose | Default |
|----------|---------|---------|
| `HUNTABLE_SIGMA_REPO_HOST_PATH` | Host checkout mounted into Docker at `/app/sigma-repo`; override only when the customer rules repo is not the app's sibling directory | `../Huntable-SIGMA-Rules` |
| `SIGMA_REPO_PATH` | Path to the customer rules repo containing Huntable-created and approved rules; used for PR submission and customer-repo indexing | `sigma-repo` |
| `GITHUB_TOKEN` | GitHub PAT for PR submission | — |
| `GITHUB_REPO` | Optional target repo override (`owner/repo`) | Saved Settings, then environment; otherwise derived from the checkout's Git remote |
| `sigmaAuthor` (Settings key) | The one `author` written on generated rules at queue entry and at PR time. Publisher-imported rules keep their own author | `Huntable CTI Studio` |

Published rules are laid out as `rules/<platform>/<logsource dir>/<slug>.yml` (generic) and `rules-emerging-threats/<family>/<slug>.yml` (rules tagged `detection.emerging-threats`). The mapping lives in the rules repo's `.huntable/rule-layout.yml`, with `config/sigma_rule_layout.yml` as the bundled fallback. See [Publish layout and metadata](../features/sigma-rules.md#publish-layout-and-metadata).

The upstream SigmaHQ reference repository is separate: `data/sigma-repo`. It is maintained by `sigma sync` for reference-rule indexing and must not be configured as `SIGMA_REPO_PATH`.

## Source Configuration

- **YAML file**: `config/sources.yaml` (version-controlled template)
- **Runtime source of truth**: PostgreSQL `sources` table
- **Auto-sync**: YAML -> DB sync runs on startup when fewer than 5 sources exist in the database
- **Add new sources without changing existing rows**: `./run_cli.sh sync-sources --config config/sources.yaml --no-remove --new-only`
- **Update existing sources from YAML while keeping DB-only sources**: omit `--new-only`, keep `--no-remove`
- **Disable auto-sync**: Add `DISABLE_SOURCE_AUTO_SYNC=true` to the web service's Compose environment

Without `--no-remove`, manual sync removes database sources missing from YAML. Use that mode only when intentionally replacing the source set.

See [Source Configuration Precedence](../guides/source-config.md) for details.

## Applying Configuration Changes

1. **Settings or Workflow editor**: Save in the UI. New workflow runs use the saved configuration; preset files and seed prompt files are not live configuration.
2. **Environment or Compose changes**: Confirm the variable is mapped into each affected service, then recreate those services. For provider changes affecting web and workflow calls:
   ```bash
   docker compose up -d --force-recreate web worker workflow_worker
   ```
   Include `scheduler` if its environment changed. A restart alone retains the old container environment. These commands briefly interrupt the selected services.
3. **Port changes**: Recreate `web`; no image build is needed:
   ```bash
   docker compose up -d web
   ```
4. **Source additions**: Sync only new entries:
   ```bash
   ./run_cli.sh sync-sources --config config/sources.yaml --no-remove --new-only
   ```

Recheck `/health` and test the affected provider or integration after applying changes. See [Source Configuration](#source-configuration) before using sync to update or remove existing sources.
